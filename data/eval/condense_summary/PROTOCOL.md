# 질문 정리 단계에 이전 답변의 요약만 넘기기 — 사전 등록

작성: 2026-11-24, 구현·측정 전. 운영 구성(EXAONE 3.5 7.8B, `configs/local.yaml`, `history_turns` 4). base는 이 커밋이다(정리 단계 지어낸 수량 검사 3ccb4a0 포함).

## 배경
질문 정리 단계(`QueryCondenser`)가 후속 질문을 독립 질문으로 다시 쓰지 않고 답변을 쓴다.
- 다중 턴 진단에서는 12개 중 3개였다(`data/eval/multiturn_check`).
- 지어낸 수량 검사 뒤에도 P11 셋째 턴에서 4회 중 2회 남았다(`data/eval/condense_facts`).
- 앞선 형식 검사는 정상 질문을 잘못 대체해 미채택이었다(`data/eval/multiturn_fix`).

개발 조사(저장소 밖 탐침, 결과를 본 사례라 채택 근거가 아님):
- 답변형 출력이 나온 기록 입력 7개를 온도 0으로 다시 돌리면, 현재 경로가 6개에서 다시 답변을 쓴다. 결함은 입력에 따라 정해진다.
- 정리 입력의 상담 답변 턴은 `요약\n분석` 전체다(턴당 500자). 답변형 출력은 분석 본문의 판단 문체를 잇는다.
- 상담 답변 턴을 첫 줄(요약)로 줄이면 6개 중 5개가 질문이 되었다.
- 기록된 답변 196개의 요약에는 줄바꿈과 근거 핸들이 없었다. 그래서 첫 줄이 곧 요약이다.

질문 모양이지만 답 내용을 담은 출력도 결함으로 센다. 예: 개발 탐침의 "…스크린샷, 관련 메시지 등과 함께 …준비해야 하나요?". 기존 분류(질문/답변)는 이것을 질문으로 셌다.

## 바꾸는 것 (한 가지)
`QueryCondenser.condense`가 정리 입력을 만들 때, 상담 답변 턴의 내용을 첫 줄로 바꾼다. 상담 답변 턴은 `role == "assistant"`이고 `evidence_ids`가 비어 있지 않은 턴이다. 함수 이름은 `condenser_view(turns)`다.
- 되묻기 턴, 보류 설명 턴(`evidence_ids` 빈 목록), 사용자 턴은 그대로 둔다.
- `render_turns`, 답변 생성 단계의 이전 대화, 프롬프트, 지어낸 수량 검사, 1,000자 상한은 바꾸지 않는다.
- 대체 경로를 새로 만들지 않는다.

## 측정

### 사례 (이 커밋에 고정, 이후 바꾸지 않음)
- `scenarios_heldout.json` Q01~Q32. 앞의 세 세트(M, N, P)와 개발 탐침의 손 사례(H1, H2)와 겹치지 않는다.
  - Q01~Q16 답변 유발형 두 턴(언제까지, 뭘 준비, 얼마까지, 어디에, 해도 되나요).
  - Q17~Q20 세 턴.
  - Q21~Q24 되묻기 뒤 답하기. Q21, Q22는 웹 형식("상담의 질문: … / 답변: …"), Q23, Q24는 평문이다.
  - Q25~Q28 주제 전환.
  - Q29~Q32 조문 대명사.
- `referent_cases.json` R01~R08: 손으로 쓴 상담 답변 턴을 가리키는 후속 질문이다. 재생 층에서만 쓴다.
  - R01~R04는 대상이 요약(첫 줄)에 있다.
  - R05~R08은 대상이 분석 본문에만 있다. fix가 대상을 잃을 것으로 예상하는 경우로, 손실 규모를 재기 위해 넣는다.

### 층과 순서
1. 종단 층(`run.py`): base, fix, base, fix 순서로 Q01~Q32를 1회씩 실행한다. 첫 base 실행은 기록 층도 겸한다. 각 정리 호출이 받은 메시지와 저장된 이전 대화를 그대로 기록한다.
2. 재생 층(`replay.py`, 주 판정): 첫 base 실행에서 모델이 호출된 모든 정리 입력과 R01~R08에 대해, 정리 단계만 base와 fix로 각각 호출한다. 두 조건의 입력은 같다. 반복은 2회다.
   - base는 fix 커밋 코드에서 `condenser_view`를 항등 함수로 바꿔 호출한다. fix 커밋의 운영 코드 변경이 `condenser_view`의 정의와 호출뿐임을 diff로 확인하고 RESULTS에 적는다.
3. 분류(`packet.py`): 입력마다 서로 다른 원래 출력 하나를 항목 하나로 만든다. 조건 표시를 빼고, 고정 시드로 순서를 섞는다.
   - 두 분류자가 서로 모르게 독립으로 분류한다. 분류자는 조건 열쇠(`-key.json`), 코드, 실행 기록을 보지 않는 별도 AI 작업자 둘이다.
   - 두 분류가 다르면 더 나쁜 쪽(A > QA > Q)으로 정하고, 불일치 목록을 RESULTS에 적는다.
   - 사람 법률 검토는 없다.
4. 판정(`score.py`): 입력·조건마다 두 반복 중 더 나쁜 분류를 쓴다.

### 분류 기준 (분류자에게 그대로 준다)
각 항목은 이전 대화, 현재 질문, 정리 결과로 이루어진다. 정리 결과는 검색에 쓸 독립 질문이어야 한다.
- Q: 독립 질문이다. 이전 대화나 현재 질문에 있는 사실과 대상만 담는다. 가리키는 말을 풀어 쓰거나, 사용자가 말한 사실을 합치거나, 질문을 그대로 쓴 것도 Q다. 끝 괄호 보충("(…기준)"), "알려 주세요"·"부탁드립니다" 같은 요청형도 Q다.
- QA: 질문 형태지만, 이전 대화와 현재 질문 어디에도 없는 답 내용을 담는다. 답 내용은 기한·기간, 절차·기관, 준비물·서류 목록, 법적 판단·결론, 법령명·조문이다. 예: 대화에 없는 "14일 이내에", "근로복지공단에", "진단서와 사고 경위서를 갖추어", "위법이므로".
- A: 질문이 아니다. 답변·설명·판단을 서술한 문장이 중심이다(물음표가 있어도 마찬가지).
- 판단이 어려우면 더 나쁜 쪽으로 분류한다.

## 판정 기준 (모두 만족해야 채택)
- G1 효과(재생 층):
  - base의 A+QA가 4개 이상이다. 4개 미만이면 "재현 부족"으로 적고 채택하지 않는다.
  - fix의 A가 1개 이하다.
  - fix의 A+QA가 base A+QA의 절반(내림) 이하다.
- G2 좋은 질문 보존(재생 층):
  - base가 Q인 입력 중 fix가 A인 것이 0개다.
  - base가 Q인 입력 중 fix가 QA인 것이 1개 이하다.
  - 지어낸 수량 검사의 대체 횟수(두 반복 합)가 fix에서 base보다 많지 않다.
- G3 지시 대상 유지(재생 층): R01~R04에서 fix 원래 출력이 두 반복 모두 `referent_any` 중 하나를 담는다(4/4). R05~R08의 결과는 판정이 아니라 한계로 RESULTS에 적는다.
- G4 근거 핸들: fix 최종 검색어(재생 층과 종단 층)에 근거 핸들 `[LEGAL SOURCE Sn]`이 0개다.
- G5 부작용(종단 층): K1~K4 각각 fix 2회 합계가 base 2회 합계보다 3개 이상 적지 않다(64개 중 base − 2까지 허용). K1~K4 정의는 `data/eval/multiturn_check/run.py`의 `check`와 같다.
- G6 지연(종단 층): 모델이 호출된 정리 턴의 `condense` 단계 중앙값이 fix에서 base보다 크지 않다(조건별 2회 합산).
- G7 저장소 테스트: `env -u PYTHONPATH -u PYTHONHOME .venv/bin/python -m pytest` 전체가 통과한다.

## 멈춤 규칙
미통과면 운영 경로를 되돌리고 측정 기록만 커밋한다. 같은 세트로 고친 안을 판정하지 않는다. 다음 후보(프롬프트 정리, 검색어 추가)는 또 다른 새 세트로 등록한다.

## 한계
- 사례 32개와 손 사례 8개다.
- 분류자는 AI이고 사람 법률 검토는 없다.
- 재생 층은 첫 base 실행의 이전 대화 위에서만 비교한다. fix에서 앞 턴 답변이 달라지는 효과는 종단 층의 K1~K4로만 본다.
- R05~R08처럼 대상이 분석 본문에만 있으면 fix가 대상을 잃을 수 있다. 실제 답변에서 그런 후속 질문이 얼마나 흔한지는 재지 않는다.
- 측정용 대화(`mt-<tag>-*`)는 실행 뒤 `cleanup.py`로 백업하고 지운다.
