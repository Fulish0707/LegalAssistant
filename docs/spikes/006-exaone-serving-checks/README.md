# Spike 006 — EXAONE 3.5 운영 전환 전 점검

날짜: 2026-11-23. 조건: bge-m3 질의 임베딩 CPU(`num_gpu 0`), EXAONE 3.5 7.8B num_ctx 12288, fp16 리랭커가 같은 프로세스에 상주(`result.json`).

| 점검 | 결과 |
|---|---|
| A. 컨텍스트 거의 가득: 프롬프트 10,630 + 출력 1,233토큰 (num_predict 2048, 모델이 스스로 멈춤) | 42.5초, 최대 7,636 / 8,188MiB, EXAONE 100% GPU, 디코드 34 tok/s |
| B. 동시 요청 2건 | 한 슬롯에서 차례로 처리됨(6.7초짜리가 16.9초에 끝남), 재적재 없음, 최대 7,642MiB |
| C. 업로드식 문서 임베딩 CPU (1,000자 × 20청크) | 10.9초 (청크당 약 0.5초) |

Ollama는 KV 캐시를 num_ctx 크기로 미리 잡으므로, 출력을 2,048토큰까지 써도 메모리가 A보다 늘지 않는다.

## API 끝단 확인 (`e2e.json`, 운영 `.env`로 `scripts/serve.py` 실행)

- 최종 테스트 질문 6개를 `/v1/chat`으로 보냈다. 모두 200, kind=answer였다. 한 턴은 17.5~34.2초, VRAM은 7,644MiB로 일정했다. EXAONE은 GPU에, bge-m3는 CPU에 있었다.
- 서버 로그 기준으로 질의 분석(QueryAnalysis)은 턴마다 5~6초다(출력 200~250토큰). 답변(LegalAnswer)은 10~26초다.
- 인용은 `answer.citations`에 들어간다(스모크 스크립트가 최상위 키를 읽어 0으로 찍혔다).
- 웹앱 ChatOllama(`OLLAMA_MODEL`): EXAONE, reasoning 미설정 상태로 응답했다. 임베딩은 `num_gpu=0`, 0.03초.

## 비용
- 업로드 문서 임베딩이 CPU에서 느려진다(청크당 약 0.5초).
- 동시 요청은 줄을 선다. qwen3:4b 때와 같은 단일 슬롯이다.
- 질의 분석 단계 5~6초가 다음 최적화 후보다.
