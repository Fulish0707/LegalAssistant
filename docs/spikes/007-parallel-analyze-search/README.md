# Spike 007 — 질의 분석과 검색 병렬화 (미채택)

날짜: 2026-11-23. 운영 구성: EXAONE 3.5 7.8B, bge-m3 질의 임베딩 CPU, fp16 리랭커 GPU, RTX 4060 8GB.

## 생각
질의 분석(1~6초)과 검색(2~3초)은 순서대로 돈다. 검색에 필요한 사용자 참조는 정규식이 대부분 찾으므로, 분석이 끝나기 전에 검색을 시작할 수 있다. 분석이 검색어를 추가하면 다시 검색해 결과를 순차와 같게 한다.

## 결과
- 구현과 테스트(916 passed)까지 했다. 최종 테스트 39문항에서 병렬/순차를 번갈아 돌리고 답변 생성 직전까지의 시간을 쟀다(`parallel_runs.jsonl`, `summary.txt`).
  - 중앙값 5.89초 대 6.06초(차이 0.1초), 평균 차이 -0.07초, p90은 병렬이 더 느림(7.29 대 6.81).
  - 근거 묶음은 38/39 동일했다. 다른 1건(q3)은 측정 실수다. 앞선 시험 실행이 같은 대화 ID로 대화 저장소에 기록을 남겨 후속 질문으로 처리됐다.
- 원인(`diagnose.py`, `rerank_share.py`): 검색 시간의 79%(턴당 약 1.5초)가 GPU 리랭커다. 리랭커와 EXAONE 디코딩이 같은 GPU를 나눠 쓴다. 동시에 돌리면 리랭커는 0.51초에서 0.91초로, 생성은 2.94초에서 3.39초로 늘어 총량이 거의 그대로다. 임베딩(CPU)은 생성 중에도 기다리지 않았다(0.03초에서 0.04초).
- 병렬로 줄일 수 있는 것은 리랭커를 뺀 약 0.4초뿐이다. 복잡도(스레드, 재검색 분기)에 비해 이득이 없어서 코드를 되돌렸다.

## 교훈
- GPU 하나에서는 GPU 단계끼리 병렬화해도 빨라지지 않는다. 먼저 단계별로 어떤 자원을 쓰는지 나눠 잰다.
- 운영 대화 저장소(`data/indexes/v1/conversations.db`)를 쓰는 측정은 대화 ID가 겹치면 후속 질문이 되어 결과가 오염된다. 측정용 대화 87개는 백업 뒤 지웠다.

## 다음 후보
턴 시간의 대부분은 답변 생성이다(10~38초). 지연을 더 줄이려면 다음을 봐야 한다.
- 답변 출력 길이(LegalAnswer 토큰 수)
- 리랭커 후보 수 축소(현재 1.5초)
- 스트리밍 체감 시간
