# 답변 초안 스트리밍 (2026-10-17)

원자료는 `data/eval/reports/chat_pipeline/streaming-2026-10-17/`에 있다. 이 폴더는 Git 제외 대상이다. 통과 기준은 실행 전에 `PREREG.txt`에 적었다. 설계는 [설계 문서](../plans/2026-10-17-answer-streaming-design.md)에 있다.

## 1. 결정

| 항목 | 결과 | 적용 |
| --- | --- | --- |
| 분석을 쓰는 동안 초안으로 보낸다 | 첫 초안 중앙값 5.6초. 최종 답변 시간, 생성 실패, 초당 토큰 수는 그대로다 | 유지 |

## 2. 무엇을 바꿨나

- 웹 채팅은 답변을 끝까지 만든 뒤 한 번에 보여 줬다. 10-10 측정에서 첫 글자까지 중앙값 17.5초였다.
- 모델은 `analysis` 필드를 먼저 쓴다. 이제 이 필드를 쓰는 동안 화면에 초안으로 보낸다.
- 초안에는 "작성 중 · 검증 전" 표시를 붙인다. 검증을 마친 답변이 오면 초안을 바꿔 쓴다.
- 재생성이나 JSON 복구 재시도가 시작되면 초안을 지운다.
- `/v1/chat`은 그대로다. 평가 스크립트는 바뀌지 않는다.
- Ollama는 JSON 스키마를 지정해도 `stream: true`로 조각을 보낸다. 마지막 조각에 토큰 수와 시간이 있다.

## 3. 시험 1: 답이 바뀌는가

고정 근거 dev-80의 앞 20문항으로 시험했다. 온도 0, seed 7, 문항마다 세 번 호출했다.

| | 스트리밍 끔 (A) | 다시 끔 (B) | 켬 (C) |
| --- | ---: | ---: | ---: |
| 모델 호출 | 22 | 24 | 23 |
| 생성 실패 | 1 | 1 | 1 |
| 초당 토큰 (중앙값) | 52.7 | 52.7 | 52.6 |

- seed를 고정해도 같은 글이 다시 나오지 않았다. A와 B가 같은 문항은 20개 중 2개였다. 그래서 글 비교 대신 실패 수와 속도로 판정했다. 결과는 통과다.
- 초안을 이어 붙인 글은 파싱된 답 19개 모두에서 최종 `analysis`와 같았다.

## 4. 시험 2: 시간

백엔드만 띄웠다(8011). 10-10 시험의 웜 질문 30개를 두 엔드포인트로 번갈아 물었다.

| | `/v1/chat` | `/v1/chat/stream` |
| --- | ---: | ---: |
| 첫 초안 (중앙값 / 90백분위) | 없음 | 5.6초 / 7.0초 |
| 최종 답변 (중앙값 / 90백분위) | 16.5초 / 31.4초 | 16.5초 / 30.9초 |
| 오류 | 0 | 0 |

- 기준 "스트림 중앙값 − 일반 중앙값 ≤ 1.0초"를 통과했다(−0.06초).
- 30턴 중 초안을 지운 턴은 없었다.
- 10-10 기준선 17.5초는 10-15 Ollama 재설치 전에 잰 값이다. 그래서 같은 시간대의 `/v1/chat`과 비교했다.

## 5. 화면에서 확인한 것

- 웹 채팅에서 첫 초안은 8.3초와 9.4초에 보였다(실제 턴 2개). 위 5.6초는 API에서 첫 줄이 온 시간이다.
- 초안이 흐르는 동안 입력창에 쓴 글과 포커스가 그대로 남는다. 처음에는 글자마다 화면 전체를 다시 그려 입력창이 새로 만들어졌다. 그래서 초안이 나타날 때와 지워질 때만 다시 그리고, 그때 입력창의 포커스와 커서를 되돌린다. 그 밖에는 초안 글자만 바꾼다. 초안이 7.2초에 나타나는 동안 계속 입력해도 글과 포커스가 남는 것을 확인했다. 그 순간 조합 중이던 한글 한 글자는 그 자리에서 확정된다.
- 초안이 흐르는 도중에 브라우저를 닫거나 새로 고치면, 처음에는 답이 저장되지 않았다(테스트로 재현). 지금은 보내기를 멈추고 턴을 끝까지 처리해 답을 저장한다.
- 인용 괄호 `(S1, S2)`는 초안에서 지운다. 최종 번호 [1]은 답이 끝나야 정해지기 때문이다. 문장 안에서 이름처럼 쓴 `S1은`은 남긴다. 지우면 조사만 남는다.

## 6. 단계 표시와 초안 상한 (사용자 요청으로 추가)

- 상태 줄은 처음에 "법령·판례 검색 및 답변 작성 중" 한 줄만 띄웠다. 이제 백엔드가 단계마다 이벤트를 보낸다. 화면은 질문 분석 중 → 법령·판례 검색 중 → 답변 작성 중 → 근거 확인 중을 보여 준다. 재생성 때는 "근거가 맞지 않아 다시 쓰는 중"을 보여 준다.
- 실제 턴 하나에서 질문 분석 중은 4.4초, 검색 중은 7.7초, 작성 중은 14.0초에 나왔다. 서버를 띄운 뒤 첫 턴이었다. 근거 확인은 수 밀리초라 거의 보이지 않는다.
- 분석 길이는 고정 근거 시험의 57개 답에서 중앙값 416자, 90백분위 1,196자, 최대 1,387자였다. 그래서 초안은 1,500자에서 더 늘리지 않는다. 반복된 초안(3,949자)은 1,500자에서 멈추고, 상태 줄은 계속 단계를 보여 준다.
- 질문을 보내면 오른쪽 근거 패널을 비운다. 전에는 초안이 나오는 동안 이전 답변의 근거 카드가 남아 새 답의 근거처럼 읽혔다. 실제 두 턴에서 초안 중에는 비어 있고, 답이 오면 5건이 채워지는 것을 확인했다.

## 7. 남은 한계

- 서버를 띄운 뒤 첫 실제 턴에서 모델이 분석 안에서 같은 말을 되풀이했다. 2,048토큰 한도에 걸렸고, 복구 재시도와 재생성이 이어졌다. 초안 상한을 넣기 전이라, 사용자는 3,949자의 초안을 약 38초 동안 보다가 그 초안이 지워지는 것을 봤다. 지금은 1,500자에서 멈추지만, 기다리는 시간은 그대로다. 시험 2의 30턴에서는 이런 일이 없었다.
- 실제 서버에서 시험한 질문으로는 되묻기 턴이 생기지 않았다. 되묻기 턴에 초안이 없다는 것은 테스트로만 확인했다.
- 후속 질문, 사건 자료가 있는 질문, 두 사용자 동시 질문은 스트리밍으로 따로 재지 않았다.
