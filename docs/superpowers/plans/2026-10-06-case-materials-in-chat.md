# 사건 자료를 상담 답변에 다시 연결 (2026-10-06)

**목표:** 사용자가 올린 사건 자료를 상담 답변이 사실 자료로 쓴다. 자료가 없는 사용자의 답변은 지금과 같다.

**방법:** Flask가 질문으로 그 사용자의 사건 자료(Chroma)를 검색한다. 찾은 조각을 `/v1/chat` 요청에 함께 보낸다. 백엔드는 조각을 법령·판례 근거와 구분된 블록으로 모델에 준다. 화면은 답변이 쓴 자료를 "내 문서" 근거 카드로 보여 준다.

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 자료의 지위 | 사건의 사실 자료. 법적 근거가 아니다 | 계약서는 법령이 아니다. 법적 근거는 계속 `[LEGAL SOURCE]`에서만 가져온다 |
| 표기 | `[USER DOCUMENT D1]`, 답변 안에서는 `D1` | 법령·판례의 `S1`과 섞이지 않는다 |
| 검색 위치 | Flask (`search_knowledge_base`) | 자료는 브라우저 ID로 나뉘어 Chroma에 있다. 백엔드는 사용자를 모른다 |
| 개수와 길이 | 조각 3개까지, 조각마다 1,000자까지. `CASE_DOCUMENT_LIMIT`, `CASE_DOCUMENT_CHARS`로 바꾼다 | 입력 한도를 12,288토큰으로 올린 뒤 쟀다. 근거가 가장 긴 질문에서 자료를 더한 입력은 최대 9,253토큰이다 |
| 입력 한도 | `num_ctx` 12,288. `LEGAL_RAG__LLM__NUM_CTX` 하나로 두 앱을 함께 바꾼다 | 8,192에서는 자료 없이도 입력 6,601 + 출력 2,048이 한도를 넘는다. 12,288에서도 모델이 GPU에 전부 올라가고(7.8GB 사용) 턴 시간은 같다 |
| 관련도 하한 | 0.25 미만인 조각은 보내지 않는다 | 계약서 한 건과 질문 8개로 쟀다. 관련 질문 0.52, 0.38, 0.34, 0.17. 무관한 질문 0.21, 0.21, 0.14, 0.12 |
| 자료가 없을 때 | 요청에 `user_documents`를 넣지 않는다 | 요청과 프롬프트가 지금과 글자 단위로 같다 |
| 인용 검증 | 자료가 법령 이름과 함께 적은 조문과 사건번호는 사용자가 직접 적은 것으로 본다. 자료 자체의 조항 번호는 답변이 법령 이름 없이 쓴 경우에만 통과한다 | 계약서 "제4조"가 "주택임대차보호법 제4조"까지 통과시키면 안 된다. 테스트로 먼저 확인하고 막았다 |
| 근거 카드 | 답변이 `D1`을 언급한 자료만 보여 준다 | 법령·판례 카드와 같은 규칙이다 |

## 규칙

- 한 커밋은 한 가지 일만 한다. 커밋마다 두 테스트 묶음이 실패 0건이다.
- 테스트를 먼저 쓴다.
- 평가 경로(`eval_chat_pipeline.py`)는 자료 없이 부른다. 동작이 달라지지 않아야 한다.
- push하지 않는다.

## 단계

### 1. 백엔드

- [x] 1.1 `UserDocument` 스키마(`name`, `text`)와 `ChatRequest.user_documents` (3개까지)
- [x] 1.2 `Orchestrator.handle(..., user_documents=())`: 생성기에 넘긴다. 자료의 글을 검증기의 `user_refs`에 더한다. 모델이 `citations`에 넣은 `D` 항목은 검증 전에 뺀다
- [x] 1.3 생성기: 자료가 있을 때만 `[USER DOCUMENT]` 블록 메시지를 넣는다
- [x] 1.4 "사용자 자료 규칙"은 자료와 함께 보내는 메시지에 넣는다 (`user_documents.md`). 시스템 프롬프트는 바꾸지 않는다. 자료가 없는 턴이 전과 같게 하기 위해서다
- [x] 테스트: 자료가 없으면 모델이 받는 메시지가 전과 같다. 자료가 있으면 블록이 들어간다. 자료에 있는 조문을 답변이 말해도 검증을 통과한다. `D` 인용이 답변을 거절로 만들지 않는다. API가 4개 이상을 거절한다

### 2. Flask

- [x] 2.1 `legal_backend.ask(..., documents=())`: 자료가 있을 때만 `user_documents`를 보낸다
- [x] 2.2 `/chat`: 질문으로 사건 자료를 검색해 보낸다. 자료 검색이 실패해도 답변은 나간다
- [x] 2.3 `legal_backend.render(body, documents)`: `D1` 표기를 근거 번호로 바꾸고 "내 문서" 카드를 만든다
- [x] 2.4 근거에 없는 인용 확인(`citation_guard`)에 자료의 글을 넣는다
- [x] 테스트: 자료가 없으면 요청 본문이 전과 같다. 자료가 있으면 본문에 들어간다. 다른 브라우저의 자료는 들어가지 않는다. 카드와 번호가 맞다

### 3. 확인

- [x] 3.1 두 테스트 묶음 실패 0건 (`tests/legal_rag` 599, Flask 118)
- [x] 3.2 실제 서버(qwen3:4b): 임대차 계약서를 올리고 물었다. 답변이 계약서의 보증금 1억 2,000만 원, 종료일, 제5조, 연 5%를 썼고 "내 문서" 카드가 나왔다. 해고 질문에는 자료를 쓰지 않았다. 요약 문장 하나가 지연 기간의 날짜를 틀렸다 (두 번 모두)
- [x] 3.3 README의 한계 항목과 흐름 설명을 고쳤다

## 하지 않는 것

- 자료의 내용으로 법령·판례 검색 질의를 만들지 않는다. 검색은 사용자의 질문으로만 한다.
- 자료만 요약해 달라는 질문(법률 분야가 없는 질문)은 지금처럼 되묻기로 간다.
- 답변 품질을 평가 세트로 측정하지 않는다. 사건 자료가 딸린 평가 질문이 없다.

## 알아 둘 것

답변 모델이 Gemini이면 사건 자료의 조각이 Google로 나간다. 로컬 모델이면 나가지 않는다.

## 진행 중에 찾은 것

한글 이름의 파일을 올리면 500 오류가 났다. `secure_filename`이 한글을 지워 `임대차계약서.txt`가 `txt`가 됐기 때문이다. 원래 이름을 표시 이름으로 쓰도록 고쳤다. 이 오류는 이 작업 전부터 있었다.

남은 위험:

- 입력 한도는 근거가 가장 긴 질문 4개와 계약서 질문 1개로 쟀다. 대화 기록이 긴 턴은 재지 않았다. GPU 여유는 약 420MiB다.
- 무관한 자료를 억지로 넣은 4턴 중 2턴에서 첫 답변이 출력 상한까지 반복하다 잘렸다. 관련도 하한이 이런 자료를 막는다.
- 후속 질문은 길이로 구분한다 (공백을 뺀 12자 이하). 직전 질문과 함께 검색한다. 계약서 한 건과 59쌍으로 잰 결과: 계약서 대화의 후속 질문은 15개 중 15개가 하한을 넘었고(그 문장만으로는 6개), 다른 화제의 후속 질문은 20개 중 0개였다(그 문장만으로는 8개). 긴 질문은 그 문장만으로 검색한다. 함께 검색하면 화제를 바꾼 질문 12개 중 10개에 계약서가 따라갔기 때문이다. 실제 서버 4턴(계약서 질문, 짧은 후속, 해고 질문, 짧은 후속)에서 자료는 앞의 두 턴에만 쓰였다.
- 길이 규칙은 내가 만든 질문으로 정했다. 13자 이상인데 내용이 없는 후속 질문은 자료를 놓친다. 12자 이하로 화제를 바꾸는 질문에는 자료가 한 턴 따라간다.
- 하한 0.25는 계약서 한 건으로 정했다.

## 4단계. 상담의 질문에 답하기 (2026-10-06 추가)

**목표:** 답변이 사용자에게 묻는 질문("추가로 확인이 필요한 사실")을 사용자가 골라서 답한다. 짧은 답("두 달이요")이 어느 질문의 답인지 시스템이 안다.

**방법:** 화면이 최신 답변 아래에 질문을 버튼으로 보여 준다. 사용자가 버튼을 누르고 답을 쓰면, 화면은 질문과 답을 한 메시지로 묶어 보낸다 ("상담의 질문: … / 답변: …"). 서버는 이 메시지를 보통 메시지로 처리한다. 묶인 문장에 주제가 들어 있으므로 사건 자료 검색과 질문 다시 쓰기가 그 문장만으로 된다.

결정:

- 답변은 미루지 않는다. 버튼은 답변과 함께 나온다.
- 서버의 답변 경로는 바꾸지 않는다. 서버는 `final_response`에 `questions` 목록만 더한다.
- 버튼을 쓰지 않고 직접 입력해도 된다. 그 경우는 지금처럼 동작한다.

체크리스트:

- [x] 4.1 테스트: `final_response`에 `questions`가 있다. 거절과 인사말에는 빈 목록이다. 설명문("…해야 합니다.")은 버튼으로 내지 않는다
- [x] 4.2 Flask: `legal_backend.questions(body)`와 `final_response.questions`
- [x] 4.3 화면: 최신 답변 아래 질문 버튼, 고른 질문 표시와 취소, 질문과 답을 묶어 전송
- [x] 4.4 두 테스트 묶음 실패 0건 (`tests/legal_rag` 601, Flask 127), 브라우저에서 화면 오류 없음
- [x] 4.5 실제 서버: 버튼을 눌러 짧게 답하는 흐름이 동작한다. 사건 자료가 붙는다

실제 서버에서 찾아 고친 것:

- 모델이 계약서에 이미 적힌 사실(계약 종료일, 보증금)을 물었다. 사용자 자료 규칙에 "자료에 적힌 사실은 묻지 않는다"를 넣었다. 그 뒤 한 번의 실행에서 질문 3개 중 2개가 사용자만 아는 사실이었다.
- 질문 다시 쓰기가 "상담의 질문"을 사용자의 질문으로 바꿔 썼다 ("임대차 계약이 실제로 종료된 날짜는 언제입니까?"). 그래서 검색이 엉뚱한 판례를 가져왔다. 다시 쓰기 프롬프트에 묶음 형식의 규칙과 예시를 넣었다. 대화 3개로 비교: 묶음 형식은 고치기 전 3개 중 1개, 고친 뒤 3개 중 3개가 처음 질문을 지켰다. 묶지 않은 짧은 후속 질문 3개의 결과는 두 프롬프트에서 사실상 같았다.
- 서버를 켠 직후 요청이 오면 재정렬이 준비 검색과 동시에 돌아 GPU 메모리가 넘쳤다 (500 오류). `num_ctx` 12,288에서 여유가 420MiB뿐이어서 드러났다. 재정렬을 한 번에 하나씩만 돌게 했다. 고친 뒤 시작 직후 동시 요청 2건이 모두 답했다.

남은 것:

- 버튼으로 답한 턴의 답변 품질은 qwen3:4b에서 고르지 않다. 한 번은 계약서와 법령에 없는 "24시간 이내 반환"을 지어냈다. 다른 한 번은 "두 달 전" 통보에 "2개월 이내에 신청하면 된다"고 답했다 (기한은 3개월이다).
- 다시 쓰기 프롬프트의 예시는 임대차 사례다. 비교에 쓴 대화 3개 중 1개가 같은 사례다.
