# KV 캐시 정밀도 시험 설계

## 목적

검증을 완료한 답변의 대기 시간을 줄일 수 있는지 확인한다. `f16`과 `q8_0` KV 캐시를 비교한다. 모델 가중치와 입력 근거는 유지한다.

## 고정 조건

- `qwen3:4b`, 동일 GGUF 및 digest. 컨텍스트 12288, 출력 2048, temperature 0.2, 전체 JSON 스키마.
- 현재 검색·분석 스냅샷, 프롬프트, JSON 복구, 인용 검증, 최종 정책을 유지한다.
- 질문 인덱스 0, 20, 40, 60, 43, 2. 예열 질문 26은 측정에서 제외한다.
- 1차 f16→q8_0, 2차 q8_0→f16. 2차 질문 순서는 반대로 한다. 총 24회 측정, 별도 예열 4회.
- paired seed = 2026101140 + round×100 + 원래 질문 위치. 후속 호출에는 호출 위치×1000을 더한다.

## 실행 경계

소유한 로컬 프로세스 `127.0.0.1:11435`만 실행한다. 각 블록은 새 서버와 예열로 시작한다. Flash Attention은 양쪽 모두 켠다. 모델 메타데이터는 별도 폴더에 복사하고 기존 블롭은 읽기 전용 경로로 참조한다. 다운로드와 prune을 금지한다. 운영 서비스의 재시작·설정 수정·모델 해제는 하지 않는다. 공유 GPU 잠금을 사용한다. 운영 모델이 실행 중이면 시험을 중단한다. 종료 시 소유한 프로세스와 runner를 정리한다.

## 판정 기준

- 속도: 두 차례 모두 생성 및 최종 정책 시간 중앙값을 10% 이상 줄인다. p90, 호출 수, 오류, 거절, 인용 재생성, 인용 제거는 늘지 않는다.
- 입력: paired 첫 호출 prompt count가 같고, 모든 호출의 prompt count + 2048이 12288 이하다. 이는 엔진 내부 토큰 전체의 독립 증명은 아니다.
- 품질: 질문·참고 답변·제공 근거 전체와 두 최종 답변 8개 필드, 완료된 초안을 모두 읽고 12쌍을 AI 검토한다. 새로운 중요 오류 또는 불확실 판정이 있으면 실패한다. 기존 공통 오류는 별도 기록한다.
- decoder tokens/sec와 출력 길이를 따로 기록한다. 답변이 짧아진 효과를 엔진 속도 향상으로 해석하지 않는다.
- 로그에서 실제 캐시 정밀도와 GPU 실행을 확인한다. 초기 로드와 예열은 제외하고, 측정 중 재시도·재로드는 포함한다.

통과해도 확대 확인 시험 후보로만 남긴다. 소규모 시험으로 운영에 적용하지 않는다.

설정 근거: [Ollama FAQ](https://docs.ollama.com/faq#how-can-i-set-the-quantization-type-for-the-k-v-cache). 캐시 양자화는 메모리를 줄이지만 정확도 영향은 모델과 작업에 따라 다르다. 속도 향상은 이 시험에서 확인한다.
