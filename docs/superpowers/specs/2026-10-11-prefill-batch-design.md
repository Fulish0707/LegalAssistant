# 입력 처리 배치 시험 설계

## 목적과 선택

동일 모델에서 `num_batch` 512와 1024를 비교한다. 긴 근거의 입력 처리와 최종 반환 시간의 변화를 확인한다. 캐시 양자화는 이전 시험에서 제외했다. 실행 엔진 교체는 설치·모델 형식 등 더 많은 변수를 수반하므로 별도 설계가 필요하다. 이번 시험은 입력 배치 하나만 바꾼다.

## 고정 조건

- qwen3:4b Q4_K_M, 동일 digest·GGUF, f16 KV, Flash Attention ON, parallel 1, GPU 37/37 레이어.
- 컨텍스트 12288, 출력 2048, temperature 0.2, 전체 스키마. 프롬프트·검색/분석 스냅샷·근거·JSON 복구·인용 검증·최종 정책 유지.
- 질문 인덱스 [0,20,40,60,43,2], 별도 예열 26. 양쪽 요청의 유일한 차이는 options.num_batch.
- paired seed = 2026101150 + round×100 + 원래 질문 위치. 후속 호출은 호출 위치×1000 추가.
- 1차 batch512→batch1024, 2차 batch1024→batch512. 2차 질문 순서 역전. 24회 측정, 4회 예열 제외.

## 실행 경계

각 블록은 소유한 새 로컬 서버 127.0.0.1:11435와 예열로 시작한다. 이전 시험과 동일한 격리 서버 생명주기를 사용한다. 별도 메타데이터, 원본 블롭의 읽기 전용 참조, 다운로드·prune 금지, 공유 GPU 잠금을 적용한다. 운영 모델이 활성 상태면 중단한다. 운영 서비스의 설정·재시작·모델 해제는 하지 않는다. 소유한 프로세스만 종료한다.

로그의 Operation:commit에서 BatchSize가 요청 값과 같고 f16, Flash Attention, 전체 GPU 레이어가 유지됨을 확인한다. 후보가 메모리 부족으로 CPU offload되면 유효한 동일 실행 조건을 충족하지 못한 것으로 기록한다. 잘린 입력 또는 context shifting이 있으면 입력 보존 실패다.

## 판정

- 속도: 두 회차 모두 최종 처리 중앙값 10% 이상 감소. p90·호출·전송 오류·거절·인용 재생성·제거 증가 없음.
- 입력: paired 첫 prompt count 동일, 모든 호출의 보고된 prompt count+2048≤12288. 내부 토큰 전체를 독립 증명한 것은 아니다.
- 품질: 모든 12쌍의 최종 8필드와 완료 초안·자동 검사 결과를 전체 제공 근거와 대조한다. 새 중요 오류 또는 uncertain이 있으면 실패. 기준부터 있던 오류는 분리한다.
- 입력 평가 시간, 디코딩 tokens/s, 출력량을 별도로 보고한다. 입력 처리 캐시 사용량은 로그에 보관한다. prompt count는 재사용 접두부를 포함하므로 count/duration을 실제 prefill 처리량으로 단정하지 않는다.
- 통과해도 확대 확인 후보로만 남긴다. 소규모 시험으로 운영에 적용하지 않는다.

설정은 [Ollama v0.16.2 API 소스](https://github.com/ollama/ollama/blob/v0.16.2/api/types.go)와 [runner 연결 소스](https://github.com/ollama/ollama/blob/v0.16.2/llm/server.go)를 확인했다. num_batch 기본값은 512이고 로드 요청의 BatchSize에 전달된다. 속도 효과는 실측한다.
